# QQ 接入实现说明（方案 B）

> 面向使用者的操作手册 + 面向排错的实现说明。
> 选型背景与第三方协议端的风险，见同目录 [`QQ接入方案.md`](./QQ接入方案.md)。

---

## 一、它做了什么

让一个**角色**（就是你在网页上配好的那个）以小号身份在 QQ 群里陪人聊天：

- 配置入口在 **个性化设置 → QQ 接入**：一个开关 + 选一个角色
- 继承该角色的**角色名、人设、角色卡设定（附加系统设定 / 示例对话）与模型参数**（温度 / top_p / 最大 token）
- 可选**知识库**（复用网页同一套 Chroma 向量库，不用重新导入）
- 可选**语音合成**（音色取角色自己的设置）
- **网页关掉也能继续回话**——真正干活的是后端常驻服务
- 支持**群聊**与**私聊**（差别见第五节）

## 二、架构与数据流

```
        ┌─────────────────────────── 你的浏览器 ───────────────────────────┐
        │  个性化设置 → QQ 接入                                              │
        │  · 开开关、选角色、勾选知识库/语音                                  │
        │  · 配置存 localStorage（唯一真相源）                               │
        └───────────────┬──────────────────────────────────────────────────┘
                        │ 推送「已解析好的配置快照」（含角色人设与模型参数）
                        ▼
        ┌─────────── QQ 接入桥接服务（FastAPI :5052，常驻）────────────────┐
        │  POST /qq/config   收配置 + 写 JSON 镜像（重启可恢复）            │
        │  GET  /qq/runtime  运行状态 / 统计 / 日志                         │
        │  GET  /audio/{name} 语音文件（给协议端拉取）                      │
        │  WS   /onebot/ws   OneBot 11 反向 WebSocket（事件入口）           │
        └───────────────┬──────────────────────────────────────────────────┘
                        │ 事件进 → 判定 → 调模型 → 动作出
                        ▼
                ┌───────────────┐        ┌──────────────┐
                │ NapCat（协议端）│        │ 大模型 API    │
                │ 小号扫码登录    │        │ Ollama/OpenAI │
                └───────────────┘        └──────────────┘
```

**为什么配置要"双写"**：桥接服务是常驻后端进程，**读不到浏览器的 localStorage**。
所以以 localStorage 为主、每次推送一份 JSON 镜像到后端。副作用是：
**必须用同一个浏览器打开过网页，后端重启后才能恢复配置**。

### 2.1 反向 WS 上跑着两种帧（排错必读）

NapCat 和本服务之间的**一条 WebSocket 上**同时跑着两类数据，看日志时要能区分：

| 方向 | 帧 | 特征 | 服务怎么处理 |
|---|---|---|---|
| 协议端 → 本服务 | **事件帧** | 一定带 `post_type`（`message` / `meta_event` / `notice` / `request`） | 这是要处理的：进判定 → 调模型 → 回复 |
| 本服务 → 协议端 | **动作帧** | 本服务发出的 `{"action":"send_group_msg",...}` | — |
| 协议端 → 本服务 | **应答帧** | **没有** `post_type`，带 `status`/`retcode`，通常带 `echo` | 这是"已收到、执行成功"的回执，**正常现象**，trace 留痕即可 |

你会在日志里看到这样的**接口应答**行，它表示消息成功发出去了（`data.message_id` 是刚发出的那条消息 ID）：

```
接口应答：status=ok retcode=0 echo=- data={'message_id': 1338174280}
```

> 早期版本把这种帧当成"事件缺少 post_type"打了 **warn**，那是误报——它不是异常数据。
> 现在只有**既无 `post_type` 也无 `status`/`retcode`** 的帧才会被报为"无法识别的帧"。
> 想看到应答行的留痕，用 `/qq/runtime?full=1`（普通视图会过滤 trace）。

### 2.2 多条连接：响应发回"哪一条"

协议端重连、或同时开多条反向 WS 都是可能的，所以连接**按 id 逐条登记**，不再是"一个槽位"。

发送动作时的候选顺序：

```
① 带来当前事件的那条连接   ← 首选（用 contextvar 传递，处理链路里不会串）
② 任意一条活连接           ← 原连接已断开时兜底
③ OneBot HTTP API          ← 最后兜底（需在配置里填 onebot.apiBase）
```

> 为什么不能用"最后连上来的那条"：旧连接可能已经死了，动作用发给它就会**静默丢失**。
> 运行状态里的 `channelCount` / `channels` 可以看到当前有哪几条连接。

## 三、快速上手

### 1. 装依赖并启动服务

```bat
:: 装依赖（已装过「知识库服务」的话可以直接启动，依赖高度重合）
install_dependencies.bat      :: 选 [7] QQ接入服务

:: 启动（任选其一）
start.bat                     :: 选 [7] QQ接入服务
:: 或手动：
cd backend_code
python qq_bot\qq_bot_api.py
```

启动成功会打印：

```
============================================================
  QQ 接入桥接服务 · 端口 5052
  NapCat 反向 WS 地址：ws://127.0.0.1:5052/onebot/ws
  NapCat HTTP 上报地址：http://127.0.0.1:5052/onebot/http
  当前配置：未就绪 — 未开启 QQ 接入
============================================================
```

### 2. 配置 NapCat

在 NapCat 的「网络配置」里新增 **WebSocket 客户端**（反向 WS）：

| 配置项 | 值 |
|---|---|
| URL | `ws://127.0.0.1:5052/onebot/ws`（跨机部署把 `127.0.0.1` 换成本服务所在机器 IP） |
| 启用 | ✅ |

> 也可以用「HTTP 上报」指向 `http://127.0.0.1:5052/onebot/http` 作为备用通道。
> ⚠️ 地址里**不要**带 `http://` 前缀给 WS 那一项——协议是 `ws://`。

> ⚠️ **改了后端代码必须重启桥接服务**。网页推送只更新"配置"（角色、参数、开关），
> **不会**热更新后端逻辑。所以拿到新版本代码后，旧服务仍在跑老逻辑——
> 哪怕界面上一切正常。排查怪现象时先重启一次。

### 3. 在网页上开启

1. 打开网站 → 右上角进入 **个性化设置 → QQ 接入**
2. 勾选 **开启 QQ 接入**
3. **接入角色**：选一个角色（只有单聊对话会出现在列表里）
4. 按需勾选 **使用知识库**（可多选知识库）与 **使用语音合成**
5. 点 **保存并推送配置**，看状态栏变成：
   - `● 协议端已连接`  ← NapCat 连上了
   - `● 配置就绪`      ← 角色和模型都齐了

### 4. 验收

在群里 **@机器人小号** 说句话，应当收到角色语气的回复。

## 四、触发策略：热闹的群怎么才不被拉黑

**默认只响应 @**。其余消息只记入上下文、**不调模型**（省钱的关键）。

判定分三层：

| 层 | 规则 | 是否能被 @ 绕过 |
|---|---|---|
| ① 闸门 | 只有 @ 机器人 / 回复机器人 才进入判定 | 本身就是闸门 |
| ② 节奏 | 同群冷却（默认 10s）、全局冷却（默认 3s）、每小时配额（默认 60 条/群） | 冷却可绕过，**配额不可** |
| ③ 抖动 | 非 @ 消息按概率（默认 25%）通过 | — |

> **为什么配额是硬上限**：@ 是用户主动点名，装死很蠢，所以冷却可以绕；
> 但被人连点 @ 时如果配额也能绕，额度几秒就烧光、还会被群友拉黑。
> 所以**每小时配额对 @ 同样生效**——这是当前版本的刻意设计。

推荐参数（新手）：
- 同群冷却 `15` 秒
- 每小时上限 `40` 条
- 单次最多回复 `1` 条
- 单条字数上限 `120`

> 想更省钱：把每小时上限压到 `20`，单条字数压到 `80`。

## 五、群聊与私聊的差别

两条链路**共用**判定逻辑、提示词构建、清洗切分、知识库与语音，
只在这几处不同——这是刻意的，避免两套代码各自漂移：

| 维度 | 群聊 | 私聊 |
|---|---|---|
| 事件类型 | `message_type = 'group'` | `message_type = 'private'` |
| 会话键 | `group_<群号>`（按群隔离） | `private_<QQ号>`（按人隔离） |
| 是否需要 @ | **需要**。没 @ 的消息连抖动层都不进，直接记入上下文 | **不需要**。私聊里每句话都是对机器人说的，视为已点名 |
| 抖动 | 非 @ 插话才走概率 | 不抖（私聊必答） |
| 冷却 | 受同群 / 全局冷却限制 | 不受冷却限制（用户私聊被"冷却"很反直觉） |
| 每小时配额 | `hourlyQuota`（默认 60/群） | `privateHourlyQuota`（默认 120/人，**独立配额**，不会被群额度挤掉） |
| 发送动作 | `send_group_msg` + `group_id` | `send_private_msg` + `user_id` |
| 提示词外壳 | 【你正在一个 QQ 群聊里】+【QQ 群聊规则】 | 【你正在和对方 QQ 私聊】+【QQ 私聊规则】 |

**上下文的隔离**：群聊上下文按群存、私聊上下文按人存，两者互不串味。
所以同一个角色在群里和私聊里，记忆是分开的（各自延续各自的对话）。

**角色锚定部分完全一致**：人设、角色卡设定、示例对话、模型参数、知识库注入都是同一套，
所以群聊和私聊里的"语气"是同一个角色——只有外壳提示词不同。

> ⚠️ 私聊配额（`privateHourlyQuota`）目前**没有做进网页面板**，需要改的话直接编辑
> `backend_code/qq_bot/data/qq_config.json`，或者用 `POST /qq/config` 推一份带这个字段的配置。
> 面板留空 / 没推这个字段时，前端推送**不会覆盖**它的默认值 120。

## 六、提示词是怎么拼的（以及为什么不用自己写角色卡）

**换壳不换芯**：角色相关部分**原样继承**，只把最外层的"群聊规则"换成 QQ 版本。

| 段落 | 来源 |
|---|---|
| 角色人设 `persona` | 直接继承角色卡 |
| 【附加系统设定】`cardSystemPrompt` | 直接继承 |
| 【角色对话示例】`cardExampleMessages` | 直接继承（对语气模仿帮助最大） |
| 用户画像 | 对话级 `userProfileName/Bio`，回退到全局「对话设定」 |
| **【QQ 群聊规则】** | **本项目自己写的 QQ 专属外壳** |
| 【可参考的知识库资料】 | 勾选知识库时注入 |

SillyTavern 宏（`{{char}}` `{{user}}` `{{date}}` `{{time}}` `{{datetime}}` `{{weekday}}`）
由后端 `render_macros()` 渲染；**未支持的宏原样保留**，绝不静默删掉（与网页侧行为一致）。

QQ 专属外壳里补了三条标准角色卡不会写、但 QQ 上必须有的约束：

1. **长度**：QQ 单条消息有上限，提示词里要求"每条消息只讲一件事"
2. **不能有链接**：模型输出里的 URL 会被 `clean_reply()` 剥掉
3. **纯文本**：Markdown 标题 / 加粗星号 / 代码围栏都会在发送前清洗掉

### 6.1 分条发送（像真人一样连发多条）

角色可以把**一次回复拆成几条连着发**。实现是**两层策略**，缺一不可：

| 层 | 做法 | 为什么需要 |
|---|---|---|
| ① 提示词层 | 要求模型在每条之间写分隔符 `|||`（三个竖线） | 模型最懂自己的断句，它配合时效果最自然 |
| ② 代码兜底层 | 按 `|||` 切分；再对仍然超长的段按句末标点切分 | **模型经常不配合**——没有这层就会发出一整坨 |

分隔符选 `|||` 的理由：正常中文聊天里几乎不会出现（不会误切正文）、
可以出现在行内不受排版影响、模型对这个 token 很熟。

容错识别：`||`、`／／`（全角）、单独成行的 `//`、单独成行的 `---` 都认。
**行内的 `//` 不当作分隔符**——它可能是路径，误切比不切更糟。

超长时的行为：先按句末标点（`。！？!?；;` 与换行）合并到接近上限，
实在切不出来才硬切——宁可断句难看，也不让消息被截断。

条数超限：多出来的内容**合并进最后一条，而不是丢弃**（丢内容比刷屏更糟）。

分条之间默认停顿 400ms：既像真人连发的节奏，也能降低频控风险。

清洗与切分顺序：

```
模型输出 → 去 <think>/<soul> → 去 Markdown → 去链接 → 去名字前缀
        → 按 ||| 分条 →（超长的按句兜底切分）→ 条数上限 → 依次发送（带停顿）
```

> 想让角色更爱分条：把「单条字数上限」调小（如 50），模型就会更频繁地断开。
> 想让它少分条：调大上限并调小「最多分几条」。

## 七、配置项一览

| 键（localStorage `qq_bridge_config`） | 默认 | 说明 |
|---|---|---|
| `enabled` | false | 总开关 |
| `sourceChatId` | null | 接入的角色（哪个对话） |
| `knowledgeEnabled` / `knowledgeIds` | false / [] | 知识库开关与选中的库 |
| `ttsEnabled` | false | 语音开关（音色取角色的 `ttsVoice`） |
| `cooldownSec` | 10 | 同群冷却 |
| `globalCooldownSec` | 3 | 全局冷却 |
| `hourlyQuota` | 60 | 每群每小时上限（硬上限） |
| `probability` | 0.25 | 群聊里非 @ 消息的通过率（当前默认外层已要求 @，此项为"允许插话"场景预留） |
| `mentionBypass` | true | @ 时是否无视冷却 |
| `replyPartMaxChars` | 80 | 单条字数上限（模型分条的参考值；超出按句兜底切分） |
| `replyPartsMax` | 3 | 单次最多分几条（私聊自动 +1，上限 10）；超出合并进最后一条 |
| `partSendDelayMs` | 400 | 分条之间的停顿（毫秒），0 = 连续发出 |
| `historyLimit` | 12 | 送给模型的历史条数 |

> 旧字段 `replySplitChars` / `maxRepliesPerMessage` 仍保留在配置里作为**回退**：
> 新字段缺失时（例如用旧版网页面板推过配置），后端的 `_part_limits()`
> 会从它们推导出单条上限与条数上限，所以老配置不会突然失效。

后端配置里另有 `privateHourlyQuota`（默认 120），是**私聊**的独立每小时配额；
网页面板目前不推送这个字段，未推送时后端保持默认值，不受影响。

后端镜像文件：`backend_code/qq_bot/data/qq_config.json`（删除它等于恢复默认配置）。

## 八、自检与排错

### 跑自检（不需要 NapCat，也不需要真模型）

```bat
cd backend_code

:: 纯逻辑自检（配置存储 / 宏 / 提示词 / 清洗 / 切分 / 触发闸门）
python qq_bot\_selfcheck.py

:: 端到端自检（需要服务已启动；会自动起一个假模型服务验证回复链路）
python qq_bot\_e2e_check.py
```

`_e2e_check.py` 会真的连反向 WS、上报 @ 消息与私聊消息，并验证：

- **服务确实把 `send_group_msg` / `send_private_msg` 动作推回给了协议端**（最容易静默出错的一段）
- 模型用 `|||` 分条时，**真的拆成多条依次发出**，分隔符不被发出去
- **多连接路由**：同时开两条连接，事件从第二条进，响应必须回到第二条
- **应答帧不会被当成异常**（打的是 trace，不是 warn）

> 想在不打扰正在运行的服务时验证：用环境变量另起一个实例即可。
> ```bat
> set QQ_BOT_PORT=5053
> set QQ_BOT_DATA_DIR=backend_code\qq_bot\_e2e_tmp
> set QQ_BOT_BASE=http://127.0.0.1:5053
> ```
> 三个变量分别覆盖监听端口、数据目录（避免污染正在用的配置）、自检目标地址。

> 自检脚本每次运行会生成唯一的 `message_id` 与假模型端口——因为服务端的
> `message_id` 去重集是**跨运行持久**的（防协议端重放），写死 ID 会让第二次运行被误判为重放。

### 全量日志

`GET /qq/runtime?full=1` 会连 **trace** 级日志一起返回——每条消息的"收到事件 → 进入处理"
都会留痕，用来区分「根本没收到」和「收到了但被判定跳过」这两种完全不同的故障。

```bat
curl "http://127.0.0.1:5052/qq/runtime?full=1"
```

### 常见现象对照

| 现象 | 原因 | 处理 |
|---|---|---|
| 状态栏显示「未连接到桥接服务」 | 5052 服务没起 | `python backend_code/qq_bot/qq_bot_api.py` |
| 显示「协议端未连接」 | NapCat 没连上来 | 检查 NapCat 的 WS 客户端 URL 是否为 `ws://127.0.0.1:5052/onebot/ws` |
| 显示「未就绪：未选择接入角色」 | 网页没选角色 / 没推送 | 面板里选好角色，点「保存并推送配置」 |
| 显示「未就绪：模型地址为空」 | 全局「模型设置」没配 | 先去 个性化设置 → 模型设置 填好主机与模型名 |
| 群里 @ 了没反应 | 被前两层拦了 | 看面板「被拦下」统计：`未被点名`/`同群冷却`/`全局冷却`/`小时配额` |
| 私聊发了没反应 | 旧版本只做群聊，私聊被整段丢弃 | 重启桥接服务（**必须重启**才加载新代码），见下方说明 |
| 一直显示「随机抖动」被拦 | 没 @ 到机器人 | 确认是真正的 @（不是手打 `@名字` 文本） |
| 重启后端后配置丢了 | 网页没推送过 | 打开网页 → QQ 接入页签 → 保存并推送配置 |
| 语音发不出来 | TTS 服务没起 / 音色不存在 | 检查 5000 端口服务，或先关掉语音开关 |
| 角色不像网页里那个 | 人设里用了未支持的宏 | 宏会原样保留，建议先用网页试好语气再复制 |
| 明明回了但对方没收到 | 发送失败只留日志 | 看日志里的「消息发送失败」——发送失败一定会打 error |
| 日志出现「接口应答：status=ok ...」 | **正常现象**：发消息成功后的回执 | 无需处理；旧版会误报成 warn |
| 日志出现「无法识别的帧」 | 协议端发了本服务不认识的帧 | 这才需要关注：把完整日志发出来看 |

### 日志在哪

- 面板内「桥接服务最近日志」折叠区（最近 8 条）
- 服务控制台（完整日志）
- `GET http://127.0.0.1:5052/qq/runtime` 最近 40 条（不含 trace）
- `GET http://127.0.0.1:5052/qq/runtime?full=1` 含 trace，排错时用这个

### 看不懂日志时按这个顺序判断

1. **有没有「协议端已连接」** → 没有就是 NapCat 没连上来（看 WS 地址与端口）
2. **有没有「收到事件 message/...」** → 没有就是协议端根本没推消息（查 NapCat 上报配置）
3. **有没有「进入消息处理」** → 没有就是被前面的类型判断挡了（例如 `post_type` 不是 message）
4. **有没有「被拦下」统计增加** → 是被触发策略拦的（冷却/配额/未被点名）
5. **有没有「回复 xxx」** → 有回复却没收到，那是发送/协议端侧的问题（会打 error）

## 九、这一版刻意没做的事

明确写下边界，避免误会：

| 不做 | 原因 |
|---|---|
| 语义判断（用辅助模型筛消息） | 热闹群里省钱靠的是"闸门 + 节奏"，拿模型筛每条消息反而更贵。等这版跑稳再加 |
| 长期记忆注入 | 网页的记忆系统在 IndexedDB + 后端 MySQL 里，**有账号体系的是可行的**，但要另做一层适配 |
| 图片生成 / 图片理解 | 多模态输入输出需要额外的上传与消息构造流程 |
| 多角色同时在一个群 | 需要按角色分别冷却与配额，编排逻辑要重做（可参考 `js/group/orchestrator.js`） |
| QQ 消息进网页聊天记录 | 需要打通 `chat_store`，属于"跨端同步"，工程量大 |
| 群聊 / 私聊共享记忆 | 两者上下文刻意隔离（群按群、私聊按人），同一角色在群里和私聊里各记各的 |
| 私聊的"仅好友可聊"开关 | 目前只要协议端把消息投递过来就会回；建议用小号并留意陌生私聊 |

## 十、安全与风险提醒

- **用小号**。第三方协议端在腾讯眼里等同外挂，账号可能被警告 / 限制 / 冻结。
- **不要把 5052 暴露到公网**。它没有鉴权——同机或内网使用；跨机请走 SSH 隧道。
- **NapCat 的 6099 管理端口同样不要暴露**。
- NapCat 协议端登录期间**不要同时登录同一 QQ 的 PC 版**（会互相挤下线）。
- 模型 API Key 会随配置推送到本服务并存进 `data/qq_config.json`：这是本地文件，
  但如果你的机器有他人共用，请注意这个文件里含明文密钥。
